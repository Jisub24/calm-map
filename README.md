# 무던한 지도 (Calm Map)

발달장애 아동 가족이 감각 자극이 덜한 시간에 외출할 수 있도록,
장소 × 요일 × 시간대별 **감각부하 지수(0~100)** 를 예측해 보여주는 서비스.

## 작업 방식

`main` 브랜치에는 **직접 push할 수 없다.** 반드시 이슈 → 브랜치 → PR을 거친다.

```
이슈 생성  →  브랜치 생성  →  작업 · commit · push  →  PR 올림  →  승인  →  main 머지
   #12        feat-12-map-ui                           (내용 검토)
```

| 용어 | 뜻 |
|---|---|
| 이슈 (Issue) | "이걸 하자"는 할 일 카드. 번호가 붙는다 (#1, #2 …) |
| 브랜치 (Branch) | main을 복사해 따로 둔 작업 공간. 여기서 뭘 하든 main은 그대로다 |
| PR (Pull Request) | "내 브랜치를 main에 합쳐주세요" 요청. 바뀐 내용을 줄 단위로 보여준다 |
| 머지 (Merge) | PR을 승인해 실제로 main에 합치는 것 |

### 순서

```bash
# 1. 최신 main 에서 시작
git switch main
git pull

# 2. 이슈용 브랜치 만들기
git switch -c feat-12-map-ui

# 3. 작업하고 커밋 (메시지 규칙은 아래)
git add .
git commit -m "Feat: 지도 화면 - 장소 표시 3단계"

# 4. 올리기 (그 브랜치를 처음 올릴 때만 -u 가 필요하다)
git push -u origin feat-12-map-ui

# 5. PR 올리기
gh pr create --fill
#   또는 push 후 GitHub가 알려주는 주소로 들어가 "Compare & pull request"
```

PR 본문에 `Closes #12` 를 적으면 머지될 때 **이슈가 자동으로 닫힌다.**
이슈 화면 오른쪽 **Development → Create a branch** 로 브랜치를 만들면 자동으로 연결된다.

### 이슈 제목 규칙

`[타입]: 페이지 이름 - 상세 내용`

예) `[Design]: 메인 페이지 - nav바 스타일 지정`

타입은 아래 커밋 메시지의 태그 목록과 같은 것을 쓴다.

### 브랜치 이름 규칙

`타입-이슈번호-페이지이름-작업종류` (타입은 소문자)

예) `feat-01-main-markup`

| 작업 종류 | 쓰는 곳 |
|---|---|
| `markup` | 사업장 웹 — 마크업 |
| `css` | 사업장 웹 — 스타일 |
| `func` | 기능 구현 (공통) |
| `ui` | 보호자 앱 — 화면. Compose는 마크업 · 스타일 구분이 없어서 `ui` 하나로 쓴다 |
| `setup` | 환경 · 설정 작업 |

### 커밋 메시지 규칙

`태그: 무엇 - 어떤 작업` 형태로 쓴다. 예) `Design: 메인 페이지 - nav바 스타일 지정`

| 태그 | 쓰는 때 | 태그 | 쓰는 때 |
|---|---|---|---|
| `Feat` | 새로운 기능 추가 | `Design` | UI/UX 변경 |
| `Fix` | 버그 수정 | `Comment` | 주석 추가 · 변경 |
| `Refactor` | 리팩토링 (기능 변화 없음) | `Chore` | 빌드 · 설정 · 환경 (CI/CD) |
| `Modify` | 코드 변경 (로직 일부 변경) | `Rename` | 파일 · 폴더명 변경 |
| `Style` | 코드 포맷팅 | `Remove` | 파일 삭제 |
| `Docs` | 문서 수정 | `Build` | 라이브러리 · 패키지 추가 |
| `Test` | 테스트 코드 작성 · 수정 · 삭제 | `Merge` | 병합 |

### PR 본문 양식

아래 틀을 그대로 쓴다. 해당 없는 항목은 **비고**라고 적는다.

```markdown
## PR 요약
(이 PR의 목적은 무엇이며, 어떤 변경이 이루어졌나?)

## 변경 내용
### **기능 추가:**
(새로운 기능에 대한 설명 없으면 비고)

### **버그 수정:**
(수정된 버그에 대한 설명 없으면 비고)

### **성능 개선:**
(개선된 부분 및 관련 데이터 없으면 비고)

### **기타:**
(기타 변경 내용 없으면 비고)

## 마주했던 문제 상황
(마주했던 문제 상황 및 해결 방법)

## 질문사항
(집중해 주길 바라는 특정 코드나 로직 없으면 비고)

## 관련 이슈
### 메인 이슈
(- `#[이슈 번호]` 형식으로 연관된 GitHub 이슈 번호를 기입)

### 참고 이슈
(- `#[이슈 번호]` 형식으로 연관된 GitHub 이슈 번호를 기입)
```

PR 제목 규칙은 추후 확정.

### 저장소가 공개라 조심할 것

누구나 코드를 볼 수 있다. 커밋 전에 항상 확인한다.

- `.env`, `local.properties`, 키가 적힌 파일 → `.gitignore` 가 막고 있지만 매번 확인
- 녹음 파일 (`analysis/recordings/`) → 원본 소리는 절대 올리지 않는다
